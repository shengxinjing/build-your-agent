## 已展开：从 Attention 到 KV Cache

在 `s00` 里，我们把完整的 `messages` 发给模型，然后等待它逐个生成新 Token。随着对话越来越长，你会发现请求通常也会越来越慢。

要理解其中的原因，需要把 HTTP 接口再向下拆一层：模型内部如何使用 Transformer 的注意力机制生成下一个 Token，以及 KV Cache 为什么能减少重复计算。

### 1. 文本先变成 Token

模型不能直接计算文字。输入文本会先经过 Tokenizer，变成一串 Token ID，再转换成向量：

```text
"Code Agent 会使用工具"
        |
        v
[Token 1, Token 2, Token 3, ...]
        |
        v
[向量 1, 向量 2, 向量 3, ...]
```

这些向量进入多层 Transformer。每一层都会通过 Self-Attention，让当前 Token 从前面的 Token 中寻找与自己有关的信息。

### 2. Attention 在做什么

在每一层中，Token 向量会分别乘以三组权重，得到 Query、Key 和 Value：

```text
Q = XWq
K = XWk
V = XWv
```

可以先用“查资料”来理解它们：

- `Query`：当前 Token 想查什么。
- `Key`：每个历史 Token 的索引特征。
- `Value`：每个历史 Token 真正携带的信息。

Attention 的核心计算可以简化为：

```text
Attention(Q, K, V) = softmax(QK^T / sqrt(d))V
```

先用当前 Query 和所有 Key 计算相关程度，再按相关程度汇总对应的 Value。生成式模型还会加上 Causal Mask，保证当前位置只能看到自己和前面的 Token，不能偷看未来。

```text
当前 Token 的 Q
      |
      v
和历史 Token 的 K 比较
      |
      v
得到注意力权重
      |
      v
按权重汇总历史 Token 的 V
```

这就是 Transformer 从上下文中寻找信息的基本过程。

### 3. 大模型如何逐个生成 Token

一次文本生成通常可以分成两个阶段。

第一阶段叫 **Prefill**。模型一次处理 Prompt 中已有的全部 Token，并为每一层计算出对应的 Key 和 Value。

第二阶段叫 **Decode**。模型根据 Prompt 预测一个新 Token，再把这个 Token 放回序列，继续预测下一个：

```text
Prompt -> Prefill -> 生成 Token A
                       |
Prompt + Token A ------+-> 生成 Token B
                              |
Prompt + Token A + Token B ---+-> 生成 Token C
```

如果没有缓存，每生成一个新 Token，都要重新处理前面整段没有变化的内容，并再次计算它们的 Key 和 Value。上下文越长，重复工作越多。

### 4. KV Cache 缓存了什么

KV Cache 的做法很直接：把每一层已经计算过的 Key 和 Value 保存起来。

生成下一个 Token 时，模型只计算新 Token 的 Q、K、V，然后把新的 K、V 追加到缓存。新的 Query 可以直接读取全部历史 K、V：

```text
Prefill
  -> 保存每层的 K1...Kn、V1...Vn

Decode 一个新 Token
  -> 只计算新的 Q、K、V
  -> 新 K、V 追加到 KV Cache
  -> 新 Q 对全部缓存 K、V 做 Attention
  -> 预测下一个 Token
```

为什么不叫 QKV Cache？因为旧 Token 的 Query 已经在它们各自生成时使用过了。未来生成新 Token 时，需要的是“新 Query 查询历史 Key 和 Value”，旧 Query 不需要重复使用。

因此，KV Cache 没有改变模型的回答逻辑，它只是用显存换计算时间，让 Decode 阶段不必反复计算相同的历史内容。

### 5. 它为什么又快又占显存

KV Cache 的大小会随着上下文长度近似线性增长。可以用下面的公式建立一个粗略印象：

```text
KV Cache 字节数
≈ 2 × 层数 × Token 数 × KV Head 数 × Head 维度 × 每个数值的字节数
  ^
  K 和 V 两份
```

所以它有一个很明确的交换关系：

- 缓存越多历史 Token，生成后续 Token 时越省计算。
- 上下文越长、并发请求越多，KV Cache 占用的显存越大。
- GQA、MQA、KV Cache 量化和 PagedAttention，都是继续降低或管理这部分成本的常见方向。

生产级推理框架不会只用一个不断扩大的数组保存缓存。例如 vLLM 的 PagedAttention 会把 KV Cache 切成块管理，思路类似操作系统的虚拟内存分页，从而减少显存碎片并提高并发能力。

### 6. KV Cache、Prompt Cache 和 messages 不是一回事

这三个概念经常同时出现，但它们处在不同层次：

| 概念 | 保存什么 | 主要作用 | 通常由谁管理 |
|---|---|---|---|
| `messages` | user、assistant、tool 等消息 | 表达对话语义 | Agent 应用 |
| KV Cache | Transformer 每一层的 K/V 张量 | 加速当前生成过程 | 模型推理服务 |
| Prompt / Prefix Cache | 相同 Prompt 前缀对应的可复用计算结果 | 减少跨请求的重复 Prefill | Provider 或推理框架 |

在当前 `s00` 中，`runChatCli()` 保存的是 `messages`。每次调用 `callLlm()`，客户端仍然会把完整历史重新发送给 Provider。

Provider 会在一次文本生成过程中使用 KV Cache，但独立 HTTP 请求之间能否复用前缀，取决于它是否支持 Prompt Cache 或 Prefix Cache。客户端不能因为上一轮问过同样的内容，就默认下一轮一定会复用 KV Cache。

### 7. 这和 Code Agent 有什么关系

Agent Loop 会反复请求模型：模型调用工具，程序把工具结果追加到 `messages`，然后再次调用模型。随着循环推进，Prompt 会不断变长。

```text
第 1 次请求：用户任务
第 2 次请求：用户任务 + tool_call + tool_result
第 3 次请求：前面全部内容 + 新的 tool_call + tool_result
```

KV Cache 可以加速一次请求内部逐 Token 的 Decode，但它不一定消除多次 HTTP 请求之间的重复 Prefill。这也是为什么成熟 Agent 还要继续考虑：

- Prompt Cache：复用多个请求共有的前缀。
- 上下文压缩：减少真正需要送入模型的历史内容。
- 工具结果裁剪：避免几万行日志占满上下文。
- KV Cache 管理：在延迟、吞吐量和显存之间取平衡。

到 `s08` 学习上下文压缩时，你会再次遇到同一个问题：历史信息当然有价值，但并不是保存得越多、每次全部重算就越好。
